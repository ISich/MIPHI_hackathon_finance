# Frontend (D3) — браузерный UI анализа изменений СПР

Vue 3 + TypeScript (strict, `vue-tsc`) + Vite 6 — стек UI по решению команды (docs v0.3). Без UI-кита, vue-router и Pinia: свой hash-router (composable) и локальное состояние экранов. Для отчётов запусков diff, pivot-итоги и distinct считает backend (D2) поверх ядра `decision_diff` (D1/D4); Python в браузере не исполняется. Отдельная рабочая область «Таблицы и сводные» рассчитывает обычные табличные агрегации локально по полному импортированному набору строк.

## Требования

Node 22 и npm (lockfile — `package-lock.json`; pnpm/yarn не использовать).

```bash
cd frontend
npm ci
```

## Запуск

| Режим | Команда | Что это |
|---|---|---|
| Реальный backend | `DD_API_TARGET=http://127.0.0.1:8000 npm run dev` | dev-сервер **только 127.0.0.1:5173**, `/api`, `/health`, `/ready` проксируются на backend-night |
| Mock (только разработка) | `npm run dev:mock` | синтетические данные `MOCK-…`, постоянный красный баннер «MOCK». **Не является реальным расчётом.** |
| Production build | `npm run build` → `dist/` | статические файлы; mock в сборку не попадает (подгружается динамически только в `--mode mock`) |

Backend запускается по его README (`backend/README.md` ветки feat/backend-night), например:

```bash
cd backend && .venv/bin/python -m dd_backend serve --host 127.0.0.1 --port 8000
```

Для стенда: UI и `/api` должны быть на одном origin (cookie-сессия `dd_session` HttpOnly, SameSite=Lax), а для `/runs/*` нужен SPA-fallback на `index.html` — ссылка из HTML-отчёта ведёт на `{DD_REPORT_UI_BASE}/runs/{run_id}/reports/{report_id}`, UI переписывает её в сводную этого Run.

## Структура `src/`

По зонам из docs/project-structure.md v0.3: `run-config/` (новый запуск), `editor/` (рабочая область, новая проверка), `run-monitor/` (список Run, мониторинг), `report-summary/`, `pivot/`, `drilldown/`, `checks-report/`; общие `api/` (типизированный клиент и DTO), `components/`, `composables/` (`useApi`, `usePolling`), `mock/` (только dev), `test/`.

Клиент перед первым запросом к `/api/*` один раз вызывает `GET /api/session` и только потом шлёт остальные: backend выдаёт новую анонимную сессию на каждый запрос без cookie, и параллельные первые запросы иначе разъезжались бы по разным сессиям.

## Экраны

Оболочка dashboard восстановлена из `feat/ui-dashboard-reference` (`7e5569e`): боковая навигация, обзор, поиск и фильтры запусков, светлая и тёмная темы. Форма входа использует её компоненты и цветовую схему.

- **Вход** — без входа UI показывает форму на любом маршруте. Локальная базовая запись: логин `admin`, пароль `admin12345`, имя «Аналитик». Вход проверяется сервером; после обновления страницы сессия восстанавливается по HttpOnly cookie. Внизу боковой панели доступны имя пользователя и выход. После входа открывается исходная ссылка, включая ссылку на отчёт.
- **Запуски** `#/runs` — список Run текущей сессии; автообновление, пока есть активные.
- **Новый запуск** `#/runs/new` — набор данных, процедура по каждому слоту (встроенная или сохранённый workspace/.py скрипт), проверки → `POST /api/configurations` → `POST /api/runs` с `Idempotency-Key` (повтор той же формы не создаёт дубль Run).
- **Run** `#/runs/{id}` — мониторинг: status/stage/substep, прогресс (при неизвестном total — неопределённый, без выдуманного %), журнал `events?after=`, код фактически исполненного snapshot по слоту. Вкладки отчёта доступны только после `COMPLETED`.
  - **Сводка** — числа из `GET /summary` этого Run, полнота checks, артефакты.
  - **Сводная** — раскладка/фильтры в URL. В `POST /pivot` отправляются `dimensions` из обеих осей, объект `filters` и `limit/offset`. Таблица строится из `items.dimensions/cnt`, drill-down использует `group_locator`. Итоги не суммируются, страницы переключаются явно. HTTP 4xx показываются как ошибки; только HTTP 501 включает совместимость с базовыми фактами D4.
  - **Проверки** — конкретный `report_id` (по умолчанию `initial_report_id`, никогда не «latest»); PASS/FAIL, приглушённый LOW, «исполнена, 0 строк» отдельно от PASS, ошибки исполнения (ERROR/TIMEOUT/INVALID_OUTPUT/…) отдельно от FAIL; K примеров APP_ID подписаны «K из CNT». HTML формируется из загруженного документа выбранного отчёта: одна общая таблица всех строк, диагностика и абсолютные ссылки на заявки с сохранением `report_id`. Файл читается без сервера; экспорт заблокирован до загрузки и проверки принадлежности отчёта запуску. В mock-режиме выгрузка помечена как демонстрационная.
  - **Новая проверка** — сразу открывается рабочий пример подсчёта доли изменённых заявок. Редактор или загрузка `.py` → сохранение (`POST /scripts` или multipart `POST /scripts/upload`) → `POST /runs/{id}/check-runs` (исходные проверки + новая) → polling → открывается **новый** report_id. Отдельная кнопка сохраняет код без исполнения. Запуск доступен, когда `GET /script-kinds` для `check` возвращает `custom_execution_enabled: true`; название режима (например, `sandbox`) UI не ограничивает. При выключенном исполнении кнопка запуска заблокирована заранее. После ошибки сети повтор использует прежний Idempotency-Key, после терминального FAILED — новый; сохранённый скрипт переиспользуется. Уход со страницы останавливает опрос и последующий запуск после незавершённого сохранения.
- **Рабочая область** `#/scripts` — скрипты всех kind, просмотр кода, создание изменённой копии/нового скрипта для слота процедуры или проверки.

Для каждого экрана есть состояния loading / empty / error / not-ready (409) / нет доступа; ответы для ранее выбранного Run отбрасываются (stale), данные выводятся только как текст.

Учётная запись настраивается на backend через `DD_AUTH_USERNAME`, `DD_AUTH_PASSWORD`, `DD_AUTH_DISPLAY_NAME` (см. [backend/README.md](../backend/README.md#account-sign-in)). Запуски и скрипты аккаунта сохраняются между входами и доступны из другого браузера с теми же данными входа. Старые анонимные данные остаются в прежней сессии и автоматически в аккаунт не переносятся. Анонимный API сохранён для совместимости; его владельцы изолированы от аккаунта.

В mock-режиме работают те же локальные данные входа; только признак входа сохраняется в `sessionStorage`, пароль туда не записывается. На macOS можно запустить настоящий API для разработки входа с `DD_EMBEDDED_WORKER=0`; расчёты требуют Linux worker.

## Таблицы и сводные

Раздел `#/datasets` доступен после входа и работает как с настоящим API, так и в mock-режиме. Таблица использует headless TanStack Table v8 с оформлением приложения, CSV/TSV читает Papa Parse, `.xlsx` — ExcelJS (загружается по запросу при импорте Excel).

- Импорт CSV/TSV с определением разделителя, заголовками в первой строке и предпросмотром; Excel с выбором листа. Формулы Excel читаются как сохранённые результаты, без выполнения формул.
- Создание пустой таблицы и демонстрационного примера, переименование, редактирование ячеек, добавление столбцов/строк, удаление выбранных строк, сортировка, поиск и пагинация. CSV-экспорт данных учитывает текущий поиск и сортировку.
- Конструктор сводной: несколько полей строк/столбцов, фильтр по значению, количество строк, сумма, среднее, минимум и максимум; итоги по обеим осям и отдельный CSV-экспорт. Все агрегации работают по полному набору с учётом фильтра. Пустые значения пропускаются для числовых показателей, нули сохраняются; среднее в итогах считается по исходным строкам.
- Существующие dataset доступны через `GET /api/datasets/{dataset_id}/table?side=before|after`. Создаётся редактируемая локальная копия текущих файлов выбранной версии: одна строка на JSON-документ (или элемент корневого JSON-массива), вложенные объекты разворачиваются в JSON Pointer-столбцы, вложенные массивы остаются JSON-текстом. Это исходные данные, а не результат нормализации или diff запуска.
- Таблицы и настройки сводной автоматически сохраняются в IndexedDB отдельно для имени аккаунта на этом origin. Сохранение локальное: данные не синхронизируются между браузерами и не изменяют серверные dataset. Очистка данных сайта удаляет библиотеку.
- Лимиты: 10 МБ на файл/серверную выборку, 20 000 строк и 200 столбцов; сводная — до 1 000 групп строк, 100 групп столбцов и 40 000 ячеек. Превышение показывает ошибку; частичные данные не выдаются за полный набор.

Проверка нового сценария: `npm run e2e:mock -- datasets.spec.ts` (desktop и narrow, CSV/Excel, редактирование, сводная, экспорт, сохранение, BEFORE/AFTER, светлая и тёмная темы).

## Тесты

```bash
npm run typecheck          # tsc strict
npm test                   # Vitest + @vue/test-utils: client, router, экраны (на тестовом дубле wire-формата)
npm run e2e:mock           # Playwright Chromium, desktop + narrow, против MOCK (UI-поведение, не расчёт)
npm run e2e:mock -- --grep 'sign in, reject'  # форма, неверный пароль, обновление страницы, выход

# реальная интеграция: backend на 127.0.0.1:8000 + dev-сервер UI
DD_API_TARGET=http://127.0.0.1:8000 npm run dev &
npm run e2e:real           # PLAYWRIGHT_BASE_URL по умолчанию http://127.0.0.1:5173
E2E_TRUSTED=1 npm run e2e:real   # только против backend с DD_EXECUTION_MODE=trusted-local на loopback
# Для проверки только входа (в том числе на macOS без worker):
PLAYWRIGHT_BASE_URL=http://127.0.0.1:5173 npx playwright test --grep 'sign in, reject'
# При изменённых данных аккаунта передайте E2E_USERNAME / E2E_PASSWORD.

npm run check:openapi -- http://127.0.0.1:8000/openapi.json   # маршруты/поля клиента есть в OpenAPI
```

Первый запуск Playwright: `npx playwright install chromium`. Отчёты: `playwright-report/`, артефакты/скриншоты: `test-results/` (в .gitignore).

## Ограничения

- Текущий pivot API возвращает counts отдельных групп и пагинацию, без итогов по осям. Прочерк в таблице означает отсутствие ячейки на текущей странице. Фактическое evidence и ограничения real E2E: [UI_PIVOT_EVIDENCE.md](UI_PIVOT_EVIDENCE.md).
- Редактор — простой `<textarea>` (Tab = 4 пробела), не Monaco и не notebook.
- Список Run загружает последние 50 (по умолчанию backend). Плитка «Всего запусков» берёт `total` из API за весь аккаунт. При неполной выборке статусы, график, поиск и фильтры явно помечены как относящиеся только к загруженным запускам.
- Суммы целых в конструкторе сводных накапливаются точно. Если итог или подытог нельзя безопасно представить числом, сводная показывает ошибку и блокирует экспорт. Среднее считается отдельно и доступно, когда его результат входит в допустимый диапазон.
- При импорте числовой строки проверяется совпадение её десятичного значения с кратчайшей десятичной записью `Number` (с учётом запятой, конечных нулей и экспоненты). `1e-400`, `9007199254740990.5` и другие строки, которые изменились бы при преобразовании, сохраняются текстом; весь такой столбец остаётся текстовым. Редактирование числовой ячейки отклоняет неподдерживаемую точность и сохраняет прежнее значение. Поддерживаемые дроби используют обычную арифметику JavaScript, а не decimal-арифметику произвольной точности.
- Real E2E проверяет выдачу одной анонимной сессии на экране входа в свежем браузере и сохранение cookie после reload. Рабочие экраны проверяются отдельно после входа; unit-тест клиента сохраняет проверку единственного bootstrap-запроса перед параллельными API-вызовами.
- Ссылки из HTML вида `/runs/{run}/reports/{report}?app_id=...` открывают указанную заявку и сохраняют контекст отчёта при возврате к сводной, в том числе после входа в аккаунт.
