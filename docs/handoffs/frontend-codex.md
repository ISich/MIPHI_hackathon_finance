## Задача 1 — выяснить причину отсутствия сети

В предыдущем отчёте из Codex не разрешались github.com и finance.corca.ru. Это **не доказывает** неисправный DNS macOS: ограничение может быть в sandbox/approval/network policy агента.

1. Прочитай git status и текущую ветку в `/Users/arthur/Hakatons/MIPHI_hackathon_finance`; чужие изменения не трогать. Не выводи приватные ключи, .env, auth.json, токены или credential-bearing remote URL.
2. В текущем sandbox повтори ограниченные read-only проверки с timeout:
   - `git ls-remote origin HEAD` в каталоге репозитория;
   - `curl -I --connect-timeout 10 --max-time 20 https://finance.corca.ru/`;
   - `curl -I --connect-timeout 10 --max-time 20 https://registry.npmjs.org/`.
3. Если sandbox блокирует сеть, запроси согласование именно этих сетевых действий через доступный approval-flow Codex. Не пытайся обходить запрет другим инструментом. Если approvals недоступны или отказаны — остановись на этом блокере и дай человеку те же команды для обычного Terminal.app, вне Codex.
4. Сравни результаты. Если Terminal работает, а Codex нет, зафиксируй ограничение среды агента; если оба не работают — исследуй DNS/сеть/VPN с человеком. **Не меняй DNS, hosts, VPN, системный proxy, SSH-ключи и не отключай sandbox целиком без установленной причины и отдельного согласия.**
5. После восстановления DNS отдельно проверь GitHub SSH/auth: ошибка DNS и отказ в доступе к приватному репозиторию — разные этапы. `gh` не обязателен; Git и веб-интерфейс PR достаточны. Не заменяй SSH remote или ключи автоматически.

Результат: конкретно воспроизводимая причина либо честный следующий блокер, а не предположение «нужно установить gh».

## Задача 3 — установить и проверить Playwright локально

Терминала с Node достаточно для программного управления браузером; встроенный browser-tool Codex не обязателен. Используй Playwright Test API (`page.goto`, `getByRole`, `click`, `fill`, assertions), а не одни HTTP-запросы/скриншоты без взаимодействий.

Перед установкой проверь package.json/lockfile. Используй один менеджер пакетов, не создавай одновременно npm и pnpm lockfiles. Изменения разрешены в своей feature-ветке. Установка JS-зависимостей и Chromium разрешена в рамках этой задачи с соблюдением approvals, но без глобальных пакетов/изменения OS. Сетевые разрешения для npm registry и загрузки браузера запроси по фактически необходимым адресам; не отключай TLS-проверки и не используй случайные mirrors.

Если frontend-пакет уже есть, добавь Playwright в него. Если пакета ещё нет, для проверки автоматизации допустим отдельный маленький tooling-пакет `tools/ui-tests/`; это **не** выбор frontend framework и не готовое приложение. Не запускай scaffold большого UI до согласования стека. Примеры команд для npm в выбранном каталоге:

```sh
npm install --save-dev @playwright/test
npx playwright install chromium
npx playwright --version
```

Для pnpm используй соответствующие команды, исходя из фактического lockfile. Сохрани зависимость и lockfile в Git, browser cache/node_modules — нет. Проверяй совместимость установленной версии с реальным Node/macOS. Не добавляй GitHub Actions/deploy workflow автоматически.

Настрой:
- Chromium, сначала headless; headed — если доступен GUI и нужно человеку;
- testDir и ясные команды запуска;
- baseURL из `PLAYWRIGHT_BASE_URL` или фактического локального dev-server, не жёстко production-адрес;
- `webServer.command` только на основе реально существующей команды package.json, не выдуманной npm script;
- screenshot при падении, trace на первый retry, HTML reporter без auto-open, конечные timeout/retry;
- pageerror/console.error и неуспешные запросы сохранять как доказательства, без секретов;
- generated reports/test-results/playwright cache в .gitignore.

Если приложения ещё нет, создай локальную **явно тестовую** HTML-страницу/сервер для проверки инструмента: поле, кнопка и результат. Браузер должен реально открыть её по localhost, заполнить поле, нажать кнопку, проверить изменившийся DOM и сохранить screenshot. Отдельно обозначь: PASS этой проверки подтверждает browser automation, **не frontend приложения**. Не выдавай тестовую страницу за экран СПР.

После появления frontend переподключи tests к реальному dev-server и добавляй сценарии: конфигурация → Run monitor → готовая summary/pivot → drill-down → checks/LOW/error → создание новой проверки. До backend разрешены маркированные API fixtures; в отчёте о тестах отличай их от реальной интеграции. Проверь desktop и узкий viewport. Отсутствующий функционал не маскируй mock-успехом.

Если Codex умеет открывать локальные изображения, посмотри screenshot. Если нет, оставь файл человеку и честно раздели проверенные DOM/assertions и визуальную оценку, которую ты не выполнял. Наличие Playwright не добавляет автоматически встроенный интерактивный browser/MCP инструмент — оно позволяет тебе управлять браузером через исполняемые Node-скрипты и тесты.

## Задача 4 — Git, коммиты и PR/MR

Существующая чистая копия main уже есть. Перед изменениями fetch/status, затем своя feature-ветка, например `feat/frontend-playwright`. Не создавать два tooling/lockfile набора независимо от команды. Локальные build/typecheck/lint/tests выполнять согласно фактическим scripts; отсутствующие команды не выдумывать.

Создай небольшой локальный коммит с конкретными файлами после тестов. В PR/MR укажи FR/задачу, что меняется, что пока отсутствует, реальные команды/вывод, SHA и как воспроизвести Playwright. Пушить только свою feature-ветку и открывать Draft PR при имеющемся разрешённом доступе; merge и deployment не выполнять. Если из Codex сеть закрыта, локальный коммит допустим, а push/PR делает человек из обычного терминала/браузера; не утверждай, что PR создан без URL.

Павел интегрирует и выкладывает на стенд по готовности несколько раз в день. Не менять finance.corca.ru, reverse proxy, серверные сервисы и доступы. Не путать локальную dev-сборку с production deployment.

4. Playwright/Chromium: версии, команда реального теста, итог assertions.
5. Screenshot/trace/report paths; что визуально проверено, а что только DOM.
6. Что создано: tooling или настоящий frontend, mocked API или реальный backend.

8. Никакого deployment/merge: это остаётся у Павла.

Официальные справки: https://playwright.dev/docs/intro и https://playwright.dev/docs/browsers . Используй актуальные установленные команды и реальные результаты, не синтетический вывод.
