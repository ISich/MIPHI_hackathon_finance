# D3 — PRD веб-приложения и интерактивной Python-области

**Owner:** D3; **reviewers:** D2 по API, D4 по аналитике. UI/компоненты/маршруты — A, обязательные возможности — [PRD](../PRD.md). Primary FR-007, FR-023; UI для FR-006,010–016,028 реализуется совместно с backend owners.

## Цель и граница

Один аналитик может настроить запуск, изменить Python-процедуру/check, следить за расчётом и исследовать завершённый отчёт без терминала. D3 не пишет diff в JS, не исполняет недоверенный Python в браузере и не копирует логику MartAPI/расчёта distinct из D4.

## Экраны и состояния

1. **Конфигурация:** dataset, процедуры по слотам, workspace/.py для каждого, параметры/exclusions/checks, сохранить/повторить/запустить. Не один глобальный переключатель источника кода.
2. **Рабочая область:** контракт, template, редактор, применение/запуск, stdout/stderr/traceback/результат. Нужна правка и процедуры, и проверки. Полноценный notebook не предполагается до решения команды.
3. **Run monitor:** status/stage, processed/total, journal, ссылка на code artifact. Unknown total = неопределённый прогресс, а не выдуманный процент. Отчёт до finalization недоступен.
4. **Summary:** число заявок/изменившихся/смен решения/различия без смены, направления, top PATH, полнота и диагностики.
5. **Pivot:** пользователь меняет строки/колонки/фильтры. Не выдавать выбор между двумя готовыми таблицами за изменяемую раскладку. Запросы к D4; total distinct не SUM(CNT).
6. **Drill-down:** group→полный набор APP_ID с пагинацией→заявка→PATH/ARRAY_KEY и сравнение before/after; контекст фильтров сохраняется.
7. **Checks:** все строки, PASS/FAIL и приглушённый LOW, отдельные execution errors, параметры; K переданных примеров не выдавать за CNT. Новая проверка в UI попадает в общий check-report.
8. **Export:** скачать серверный HTML; ссылка из локального файла ведёт именно в сводную соответствующего Run. ИИ-секция только в последнем этапе работ; отсутствие честно обозначено.

## Технические требования к UI

[API draft](../contracts/api.md) согласовать с D2 до интеграции. Loading/empty/error/forbidden/not-ready состояния обязательны для каждого экрана. Экранировать Python output и значения JSON/LLM. Никаких upstream-токенов в frontend bundle. Polling или events — выбор команды; stale ответы не должны подменять уже выбранный другой Run.

Fixture mode допустим только как маркированная среда разработки с теми же DTO. Не показывать mock-results на стенде как настоящий расчёт. После появления минимального API перейти на него сразу, не в финале.

## Задачи

- **D3-01:** утвердить DTO с D2/D4; выбрать frontend/pivot по решениям команды. Начать route skeleton/API client и обработку ошибок.
- **D3-02:** конфигурация, script source selector на слот и рабочая область; фактическое применение кода через D2.
- **D3-03:** monitor/journal/code и первый реальный run_id; без ожидания готовности всех графиков.
- **D3-04:** summary/pivot и membership pagination; totals проверить с D4 на заявке в нескольких группах.
- **D3-05:** карточка заявки/атрибута, checks/LOW/errors, новая проверка из UI и export.
- **D3-06:** браузерный сценарий двух сессий и девять шагов защиты; UX smoke после интеграции.
