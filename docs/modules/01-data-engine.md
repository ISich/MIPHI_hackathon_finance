# D1 — PRD данных, нормализации и сравнения

**Owner:** разработчик D1, человек пока не назначен. **Reviewer:** D4 по схемам, D2 по исполнению/хранению. Реализация и структура — A; обязательные результаты наследуются из [общего PRD](../PRD.md), §§6–8. Основные FR: FR-002, FR-004, FR-005, FR-019, FR-020, FR-021.

## Результат и границы

Выбираемые пользовательские Python-процедуры превращают два среза JSON в vertical normalized rows, логическое comparison view и segments. Платформа не содержит зашитые пути СПР. D1 не делает HTTP, UI, очередь, общий DB driver и запуск checks; это D2/D3/D4.

## Вход → выход

- Вход: dataset descriptor от D2, read-only файлы/пары APP_ID, SOURCE, параметры, исключения, режимы массивов и бакеты.
- Выход: артефакты [data contract](../contracts/data.md) и диагностики через [execution contract](../contracts/execution.md). Ссылки на артефакты передаются D2; D4 читает завершённые rows через согласованный storage port.
- Метаданные Run/owner не подменяются бизнес-полями. Хранилище/модель передачи согласовываются с D2, dataset-specific код находится в `user-code/processing/`.

## Правила

1. До нормализации проверить пары по имени файла без расширения; не прибивать 2002 или RUN ID к коду. Ошибки пар/ключей/JSON возвращать диагностикой; строгую политику FAILED применяет D2.
2. Исключения request_id/createDateTime настраиваются. Бакеты одинаковы для обоих срезов, diff по исходному VALUE.
3. Массивы: key/composite-key, scalar-value, positional-vector. Полная таблица девяти массивов — PRD §7.2. modelName и вложенные ARRAY_KEY не терять. Смена ключа = LOST+NEW.
4. Путь для MartAPI без `[]`; boolean/null сериализуются `true`/`false`/`NULL` совместимо с checks. Missing/type не склеивать молча. Неутверждённая числовая/типовая политика из PRD Q5 остаётся явной настройкой и вопросом, не «проверенным эталоном».
5. Одна comparison-строка на APP_ID/PATH/ARRAY_KEY. Один CHANGE_TYPE из четырёх, DIFF_FLAG согласован с ним. Исчезнувшие/новые листья не превращать в смену пустой строки.
6. Segments: одна строка на заявку со всеми полями PRD §6.3; PRODUCTS через `;`; DECISION_CHANGED bool/0/1, не строка. Решение заявки — decisionResult.decision. Для нескольких продуктовых PD/cutoff нужна документированная проекция, а не случайный первый элемент.
7. Технический UNION остаётся вертикальным; comparison — совместимая проекция. Физическую материализацию не принимать молча как закрытый Q2.

## Задачи, порядок и доказательства

- **D1-01:** согласовать схемы с D4/D2; передать минимальные paired JSON и ожидаемые rows для всех четырёх типов. Готово: fixture/expected проверяются тестом.
- **D1-02:** reader и normalizer одной пары, configurable exclusions и flat paths. Зависимость: execution inputs D2. Готово: реальные rows от процедуры, не вручную подготовленный CSV вместо расчёта.
- **D1-03:** key/composite/scalar/index arrays, modelName; negative tests дублей/отсутствия ключа и тест перестановок. Готово: порядок key-массива не меняет результат, вектора — меняет.
- **D1-04:** comparison и segments; missing/null/bucket tests; согласованный storage artifact. Зависимость: data contract.
- **D1-05:** прогон полного открытого набора через D2; independent decision-count cross-check; проверка uniqueness и наборов ID. Готово: фактический результат/ошибки и измерения приложены к PR; эталонный N_changed не заявлен без организаторов.

## Приёмка и передача

AC-02…AC-08 основного PRD — ядро ответственности; AC-01/09/18 совместно с D2/D4. Каждый PR содержит тест, фактическую команду и вывод, затронутые FR и семантические решения. Передать D4 маленькие действительные rows+segments в начале работы; не ждать всех массивов. Поставить простую штатную процедуру как заменяемый script artifact, чтобы D3 мог изменить её через UI без пересборки backend.
