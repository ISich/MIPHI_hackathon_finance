# PRD — система анализа изменений СПР

**Версия: 0.3 — итоговая редакция анализа для согласования.**  
**Область:** модули 3 и 4 хакатона МИФИ. **Горизонт:** двухдневный прототип.  
**Статус:** требования первичных материалов отделены от проектных решений. Ответы на вопросы §16 и выбор стека **не утверждены командой или организаторами**. Документ не подтверждает наличие готовой реализации и не разрешает промышленное использование.

## 1. Назначение и результат

Веб-приложение принимает уже полученные ответы одной СПР на одинаковые заявки в двух версиях стратегии: BEFORE / MASTER и AFTER / BETA. Пользователь выбирает процедуры обработки и проверки, запускает расчёт и получает:

1. Сводку: сколько заявок изменилось, у скольких сменилось решение и в каком направлении.
2. Настраиваемую сводную таблицу поверх агрегированных фактов counts.
3. Переход от показателя к заявкам и конкретному атрибуту до/после.
4. Единую таблицу результатов выданных и авторских Python-проверок; скачиваемый HTML с переходом обратно в приложение.
5. Прогресс и журнал с переходом к коду этапа.
6. Независимое мнение ИИ рядом с детерминированными результатами — статус обязательности уточняется, но молчаливое исключение из задания недопустимо.

Приложение помогает аналитику оценить последствия изменения **до выкладки**, но само не решает, безопасна ли выкладка, и не изменяет стратегию.

## 3. Пользователи и продуктовые сценарии

**Владелец Decision Flow:** оценить масштаб и направление эффекта перед выкладкой.  
**Аналитик:** выделить сегмент, проверить гипотезу и исследовать значения.  
**Автор процедур/checks:** изменить Python-код, параметры и повторить расчёт.  
**Жюри:** воспроизвести запуск, подменить данные или check и проверить корректность.

После открытия готового отчёта аналитик должен за минуту найти ответы [S2, «Что значит отчёт и сводная таблица»]:

- Сколько уникальных заявок изменилось и у скольких сменилось решение?
- Какие атрибуты меняются чаще, какие продукты/партнёры/сегменты затронуты?
- Какие изменения правил, баллов или порогов наблюдаются у заявок со сменой решения?
- Где различия есть, а решение осталось прежним?

**Ограничение объяснимости:** совместное изменение внешнего скора и решения — наблюдаемая связь, а не доказательство причинности. Интерфейс показывает факты, результаты checks и ссылки на атрибуты; не объявляет точную причину без соответствующего метода.

Сбор ретро-пулов, вызов СПР, редактирование стратегии, автовыкладка, универсальная ETL-платформа для любого JSON/XML, обязательные микросервисы, enterprise IAM/HA, полноценная история версий кода.

- ИИ-мнение описано отдельным блоком без текстовой отметки «необязательно» [S1, с.11; S2, «Альтернативное мнение от ИИ»]. ## 6. Логическая модель данных и арифметика отчёта

### 6.1. Разделение слоёв — предлагаемое разрешение конфликта источников

S1/S2 требуют вертикального datamart, а S4 и пять checks требуют строки с VALUE_BEFORE/AFTER. Это не разрешает игнорировать ни один из контрактов.

**A/Q2: предлагается пять логических слоёв:**

1. **Normalized / UNION:** одна существующая листовая величина одной заявки одного среза. Поля учебного формата: APP_ID, SOURCE, PREFIX, CLASS, SUFFIX, ARRAY_KEY, KEY, VALUE, ADJUSTED_VALUE; PATH хранится или выводится однозначно. Источник SOURCE = BEFORE или AFTER. Ключ — Run + SOURCE + APP_ID + PATH + ARRAY_KEY.
2. **Comparison view:** одна логическая пара атрибутов по APP_ID + PATH + ARRAY_KEY. Поля S4: APP_ID, PREFIX, CLASS, SUFFIX, ARRAY_KEY, KEY, PATH, VALUE_BEFORE, VALUE_AFTER, ADJUSTED_BEFORE, ADJUSTED_AFTER, DIFF_FLAG, CHANGE_TYPE. Это представление для MartAPI и деталей, а **не горизонтальная замена технического UNION**. Физически предпочтительно вычисляемое/индексируемое представление над вертикальным слоем; допустимость отдельной материализации уточнить Q2.
3. **Segments:** одна строка на APP_ID по схеме S4, без размножения строки заявки на продукты.
4. **Report facts:** группы по измерениям сводной со SOURCE, бакетом/значением, признаком/типом изменения и числом заявок CNT; отдельно сохраняется точное множество APP_ID или индекс, позволяющий его восстановить.
5. **Check results / executions:** контрактные строки и отдельные технические метаданные исполнения.

Ориентир «около 290 тысяч строк» относится к логическим сопоставленным атрибутам. Число вертикальных строк считается отдельно по факту нормализации; его нельзя автоматически приравнивать к числу сравниваемых пар или использовать как точный эталон.

### 6.2. Определения метрик

Для валидного полного запуска после исключений:

- `N = число уникальных APP_ID` в наборе обработанных пар.
- `N_changed = |{APP_ID: существует comparison-строка с DIFF_FLAG=1}|`.
- `N_decision_changed = |{APP_ID: DECISION_BEFORE != DECISION_AFTER}|`.
- `N_changed_same_decision = |{APP_ID: есть DIFF_FLAG=1 и DECISION_CHANGED=0}|`.
- Число изменившихся **атрибутов** — число логических comparison-строк с DIFF_FLAG=1; это не число заявок.
- Для группы G: `CNT(G) = число уникальных APP_ID, принадлежащих G`. Drill-down возвращает именно это множество, с пагинацией.

**Инварианты:** четыре CHANGE_TYPE разбивают множество comparison-строк без пересечений; DIFF_FLAG=0 только при SAME; N_changed≤N; при обязательном сравнении decisionResult.decision множество со сменой решения входит в множество с различиями.

**Неаддитивность:** одна заявка может иметь несколько атрибутов, продуктов, правил и два SOURCE. Поэтому сумма CNT по произвольным ячейкам не равна числу заявок. Итоги distinct-заявок считаются объединением множеств APP_ID/повторной агрегацией, а не SUM(CNT). Если компонент умеет только SUM, такая сумма подписывается «атрибутные вхождения», а неверные итоги по заявкам отключаются. Добавить отдельный корректный distinct-показатель.

Новый атрибут имеет существующую строку AFTER, исчезнувший — BEFORE. Не создавать фиктивную исходную строку отсутствующего среза ради симметрии counts. В сравнении оба случая остаются одной логической строкой.

### 6.3. Слой разрезов

Обязательные поля [S4, §2]: APP_ID; DECISION_BEFORE/AFTER; DECISION_CHANGED; PRODUCTS; TOP_OFFER_BEFORE/AFTER; PARTNER_TYPE; ROUTING_METHOD; PD_MODEL_BEFORE/AFTER; CUTOFF_BEFORE/AFTER; REJECT_REASON_BEFORE/AFTER; SCORE_OKB_BEFORE/AFTER.

**C:** выданный `ar_drop_by_product` ожидает PRODUCTS как строку продуктов через `;`; DECISION_CHANGED должен быть числом 0/1 или bool, но не строкой `"0"`. Checks зависят от наличия всех обязательных полей.

**A:** правило выбора/агрегации продуктовых полей в одну строку заявки документируется в пользовательской процедуре, детерминированно и без произвольного «первого элемента». PRODUCTS предлагается получать как отсортированное множество ID из обоих срезов. TOP_OFFER — по минимальному rank. Если разные продукты дают несколько PD_MODEL/CUTOFF/PARTNER_TYPE/ROUTING_METHOD, нельзя молча терять значения: требуется явная согласованная политика проекции. Полный продуктовый контекст сохраняется в нормализованных атрибутах независимо от проекции.

В проверенном открытом наборе у заявок несколько продуктов, но внутри каждого среза одной заявки обнаружено одно уникальное имя pd-модели. Это наблюдение **не** разрешает предположить то же о закрытом наборе. Семантика неоднозначной проекции вынесена в Q5.

## 7. Семантика нормализации и сравнения

### 7.1. Обязательные правила

- Структурная идентичность: `(APP_ID, PATH, ARRAY_KEY)` в comparison; modelName входит в ARRAY_KEY соответствующей модели/предиктора [S3/S4]. Переименование ключа элемента — исчезновение старого и появление нового, а не случайная склейка.
- Вложенные ключи массивов сохраняют весь контекст по пути, через `|`; у rules ожидается `<product_id>|<rule_name>` — это использует исходник check.
- Равные значения на разных стадиях скоринга остаются разными атрибутами: ext_data, characteristics, features не дедуплицируются [S3, «Три этапа скоринга»].
- DIFF_FLAG определяется исходным VALUE; ADJUSTED_VALUE используется только для группировки. Бакеты одинаковы в обоих срезах, правила и границы задаёт процедура пользователя.
- Технические поля по умолчанию исключаются на нормализации. Сырые JSON могут сохранять их для диагностики, но они не попадают в сравниваемую витрину.
- product_catalog и tariff_matrix разрешено исключить с обоснованием [S3]. **Предлагаемый default:** не исключать, чтобы не скрыть изменения справочников; переключение явно влияет на конфигурацию расчёта.

### 7.2. Правила массивов из S3

| Путь массива | Режим | Ключ |
|---|---|---|
| decisionResult.available_offers[] | По полям | product_id + type |
| decisionResult.product_trials[] | По полю | product_id |
| decisionResult.product_trials[].rules[] | По полю | name |
| decisionResult.product_trials[].scoring.scoreModels[] | По полю | modelName |
| decisionResult.scoring[] | По полю | modelName |
| decisionResult.scoring[].value[] | По индексу | индекс вектора |
| ext_data[] | По вложенному полю | body.action |
| product_catalog[] | По полям | mfo_id + product_id |
| tariff_matrix[] | По полям | mfo_id + product_id |

**Третий режим — по значению:** для массивов скаляров с незначимым порядком ключом служит сам элемент. Он необходим для поддержки учебного примера и пользовательских схем; не заменяет индексный режим вектора модели. Режим никогда не угадывается только по форме JSON.

**A:** отсутствующий ключ или дубликат составного ключа в одном массиве — ошибка данных, а не last-write-wins. При режиме по значению предлагается явно объявленная семантика множества; дубли либо отвергаются диагностикой, либо обрабатываются отдельным согласованным multiset-режимом. Разделители и типы частей ключа кодируются однозначно, без коллизий. У вектора лишние хвостовые позиции дают NEW/LOST, перестановка значений по индексам даёт VALUE_CHANGED.

### 7.3. Отсутствие, null, типы — предлагаемые defaults

S3 оставляет `rules[].hit: null→false` решением команды с обоснованием. Остальные пробелы нельзя молча выдавать за норматив.

**C, совместимость исходников checks:** PATH не содержит `[]`/индексов; ожидаются, в частности, `characteristics.score_okb`, `decisionResult.scoring.features.score_okb` и `decisionResult.product_trials.rules.hit`. Для boolean и null проверки буквально ожидают строки `"true"`, `"false"`, `"NULL"`, а ключ правила — `<product_id>|<rule_name>`. Числа на разных путях сериализуются одинаково, иначе сравнение feature с источником даст ложное расхождение. Эти соглашения не произвольный выбор UI; отклонение ломает выданный код.

**A, до подтверждения Q5:**

- Отсутствующее поле не равно JSON null, пустой строке, false или нулю.
- Наличие хранится отдельно от отображаемого VALUE. Boolean/null сериализуются по обязательным соглашениям выше; отсутствие стороны — пустое значение по S4. Настоящий текст `"NULL"` не склеивается с null внутри движка при выбранной типизированной семантике.
- `hit: null→false` считать VALUE_CHANGED: «не вычислялось» отличается от «вычислено и не сработало». Обоснование и настройка видны в конфиге/отчёте.
- Число и строка с тем же написанием различаются; bool и число различаются. Числа сравниваются как JSON-числа без неявного epsilon; 1 и 1.0 равны численно. Даты не преобразуются без явно заданного правила. NaN/Infinity не принимаются как стандартный JSON.
- Пустые массивы/объекты сами не создают листовой атрибут; отсутствие→пустая коллекция при таком default не даёт листового изменения. Если требуется различать структуру пустых контейнеров, это расширение общего контракта с тестами совместимости, не скрытый sentinel в бизнес-данных.
- При смене контейнера на скаляр старая совокупность листьев исчезает, новый лист появляется; не подгонять несовпадающие пути под VALUE_CHANGED.

Тип и признак наличия могут быть внутренними дополнительными полями. **A/Q5:** сравнение с учётом типа расширяет смысл строкового VALUE в S4: при одинаковом отображении числа 1 и строки "1" возможны равные строковые VALUE и разные типизированные значения. Это не выдаётся за подтверждённое правило эталона. До утверждения команда должна согласовать либо однозначное check-совместимое строковое кодирование типов, либо явное расширение comparison-схемы/семантики. Вопрос о числах 1/1.0 и типах 1/"1" включён в Q5; соответствующий тест условен до выбора политики.

## 8. Контракты пользовательского Python

### 8.1. Граница платформы

Платформа знает общие схемы строк, Run, вызов runner, хранилище, MartAPI и отчёты. Специфические пути СПР, исключения, ключи массивов, извлечение разрезов и бакеты — в выбираемых Python-процедурах и их параметрах. Поставить начальную процедуру для текущего формата можно; зашивать её в незаменяемый backend нельзя.

Для normalize/compare/aggregate пакет не выдаёт готовых функций с фиксированными именами. **A:** до параллельной разработки команда фиксирует собственный маленький документированный интерфейс:

| Вид | Логический вход | Обязательный выход |
|---|---|---|
| Normalize | Документ/набор, APP_ID, SOURCE, параметры | Валидные нормализованные строки и диагностики |
| Compare | Вертикальные строки и правила сравнения | Сопоставление с четырьмя CHANGE_TYPE, доступное MartAPI |
| Aggregate | Сопоставление, вертикальные строки, разрезы | Counts и восстанавливаемые группы APP_ID |
| Check | MartAPI и params | list[dict] по S4/S5 |

Эта таблица — проектный контракт, не выдуманная сигнатура организаторов. Формат передачи, имена entrypoint и типы контейнеров фиксируются командой в репозитории вместе с примером и валидатором.

### 8.2. Два канала кода

**M:** интерактивное написание/правка и немедленное применение **процедуры и проверки**; выбор размещённого `.py`. Наличие одного textarea без выполнения не покрывает интерактивную область.

**A/Q3:** минимальная область — встроенный Python-редактор, шаблон, параметры, кнопка запуска/применения, stdout/stderr/traceback и показ результата. Полноценные Jupyter server/kernel, произвольные pip-install и скрытое состояние ячеек не включать без подтверждения. Каждый production-like запуск выполняет сохранённый текст в чистом контексте, не зависит от истории действий редактора.

**A:** конфиг запуска фиксирует выбранный источник для каждого обработчика. Снимок текста/параметров создаётся при старте; последующая правка не меняет уже исполняемый код. Повтор «текущим кодом» и повтор «снимком запуска» явно различаются, если реализованы оба.

### 8.3. Точный контракт checks

Каждый выданный файл экспортирует:

```python
CHECK = {
    "id": "unique_id",
    "label": "Название",
    "params": {...},
    "entrypoint": run,
}
# entrypoint вызывается как run(mart, params) -> list[dict]
```

Обязательные поля строки: LABEL, SOURCE, ARGUMENT, CNT, TOTAL, METRIC, APP_IDS, RESULT, CONFIDENCE. SOURCE — только BEFORE/AFTER; межсрезовый check использует AFTER. RESULT — только PASS/FAIL. CONFIDENCE — HIGH/LOW. Идентификатор исполнения/check_id можно хранить рядом как метаданные, не меняя исходников.

```python
mart.rows(**filters)    # Iterable[dict], строки comparison
mart.count(**filters)   # int: число СТРОК, не distinct-заявок
mart.app_ids(**filters) # list[str]: уникальные APP_ID, отсортированные
mart.segments()        # Iterable[dict]: одна строка на заявку
mart.total_apps()      # int: число заявок данного запуска
```

Фильтры S5, все необязательные и соединены **И**:

- path: точный PATH или список; path_prefix: начинается со строки;
- key, array_key: точное значение;
- diff_flag: 0/1;
- change_type: один тип или список;
- value_before, value_after: точное контрактное значение;
- app_ids: ограничение набором заявок.

**A:** пустой список фильтра даёт пустое множество, неизвестный фильтр — диагностическую ошибку; никогда не игнорировать неизвестный ключ. array_key сравнивается с полным ARRAY_KEY; это выбранный default, не доказанная семантика неизвестной проверки жюри. rows/count/app_ids при одних фильтрах согласованы; порядок rows фиксирован по `(APP_ID, PATH, ARRAY_KEY)`. Проверки всегда видят только один заданный Run. Параметры CHECK копируются перед переопределением для конкретного запуска: общий объект DEFAULTS не мутируется между пользователями/Run. Нужны индексы; полный проход по всей витрине на каждый вызов не считать целевой реализацией.

### 8.4. Семантика пяти выданных checks

1. **ar_drop_by_product:** группирует по PRODUCTS, но сравнивает **решение заявки** DECISION_BEFORE/AFTER среди заявок с продуктом. Это не approval rate поля product_trials[].decision. CNT — число заявок APPROVE→не APPROVE, METRIC — относительное падение AR; не обязаны равняться CNT/TOTAL. При нулевом исходном AR код возвращает нулевое падение — сохранить поведение исходника.
2. **attribute_new_loss:** уникальные APP_ID по PATH и типу NEW/LOST; порог min_share. При отсутствии выходных проблемных групп создаёт PASS. Не равно числу изменённых листьев.
3. **external_score_drift:** пересечение изменившегося score_okb и смены решения; дополнительно сравнивает feature со внешним скором. Это эвристика, не причинное доказательство. В исходнике features индексируются только APP_ID: если один feature встречается у нескольких моделей, возможна перезапись. Сортировка rows должна быть детерминированной, но это не исправляет логическую неоднозначность; запросить ожидаемую политику и не схлопывать modelName в данных ради check.
4. **stop_factor_disappeared:** потеря hit=true или переход true→false/NULL. Внутри вычислены два вида событий, но переменная title не включена в возвращаемую строку; при совпадении ARGUMENT два события могут выглядеть одинаково. Не дописывать невыданное бизнес-поле за check: различие раскрывается в деталях comparison/собственной дополнительной проверке.
5. **target_model_changed:** использует PD_MODEL_* слоя разрезов. Код вычисляет with_cutoff, но отдельный результат об изменении порога не возвращает. Нельзя обещать такой результат от выданного check; изменение порога видно в деталях или отдельной авторской проверке.

**M/C:** исходники исполняются как есть; найденные ограничения документируются. Новую исправленную/расширенную проверку можно добавить под отдельным CHECK.id, не подменяя тихо выданную.

**APP_IDS:** выданные checks по умолчанию ограничивают список двадцатью примерами через app_ids_limit. UI показывает «передано K примеров», а не «это все CNT заявок». Для полного drill-down произвольного check одного APP_IDS может быть недостаточно: расширенный locator/множество — отдельный контракт команды. Обязательный переход из проверки покрывает переданные APP_IDS; переход из counts — полное множество группы.

## 9. Интерфейс и результаты

Минимальные экраны/области:

1. **Конфигурации и запуски:** датасет, обработчики, один источник каждого, параметры checks, сохранить/повторить/запустить.
2. **Python-область:** код процедуры/check, контракт, параметры, выполнить, диагностика.
3. **Мониторинг Run:** этап, объём, журнал, код; отчёт недоступен до финализации.
4. **Обзор:** метрики §6.2, направления решений, наиболее частые изменённые PATH, статус расчёта/checks/ИИ.
5. **Сводная:** перестановка измерений; SOURCE, путь/его части, ARRAY_KEY, значение/бакет, CHANGE_TYPE/DIFF_FLAG и доступные разрезы. Неоднозначные многозначные поля не теряются молча.
6. **Drill-down:** сохранённый контекст фильтров, список ID, карточка заявки, сравнение атрибута с признаком отсутствия, а не неразличимой пустотой.
7. **Проверки:** все строки всех выбранных checks, параметры/происхождение, вердикт и уверенность, ссылки на переданные примеры, экспорт; отдельный блок ИИ-мнения в этом же отчёте, если функция включена, либо явный статус его получения.

LOW визуально приглушается, но RESULT=FAIL не меняется. Значения, traceback и HTML экранируются. Экспорт содержит Run ID, параметры/полноту, все строки и заметные технические ошибки; **A:** отдельную секцию с готовым ИИ-мнением или состоянием «не включено / ещё не получено / ошибка» на момент выгрузки. Внешняя ссылка ведёт именно в сводную соответствующего Run и работает только при доступном приложении и по согласованной политике доступа: офлайн-файл не обещает офлайн-работу самого приложения.

Для сценария добавления проверки **A:** новый check-run на готовой неизменной витрине включает исходный набор плюс новый check и публикует новую ссылку. Допустим и полный повтор, если он укладывается в демонстрацию; mutable-дописание старого отчёта по той же ссылке не является default.

## 10. Жизненный цикл и ошибки

**A:** Run имеет отдельный status: QUEUED, RUNNING, COMPLETED, FAILED; внутри RUNNING — stage: VALIDATING, NORMALIZING, COMPARING, AGGREGATING, CHECKING, FINALIZING. ИИ-обогащение имеет отдельное состояние и не переписывает завершённые deterministic-результаты. Отмена/возобновление после рестарта сервера — не обязательное расширение.

### Предлагаемая строгая политика для хакатона

- Нет пары, невалидный JSON, неоднозначный ключ, нарушение выходной схемы нормализации/сравнения — FAILED с явной диагностикой. Проверка manifest ограничена реально используемыми объявленными полями: доступность каталогов срезов и соответствие заявленного applications фактическим полным парам, если поле присутствует. Не требовать неизвестную схему manifest, фиксированный RUN ID, дату или ровно 2002 на новом наборе; правила регистрации нового набора документируются. Не публиковать «полный» отчёт на молча отброшенных заявках.
- Падение агрегации/хранилища/финализации — FAILED; предыдущий готовый отчёт другого запуска не выдаётся за новый.
- Исключение/таймаут/невалидный результат одного check — отдельный execution_status ERROR/TIMEOUT/INVALID_OUTPUT. Остальные checks могут завершиться. После окончания всех выбранных исполнений допускается готовый отчёт с заметной пометкой «проверки выполнены не полностью»; такой запуск не проходит позитивный критерий исполнения всех пяти checks.
- В схему RESULT не добавлять ERROR: в общей таблице это техническая диагностическая запись/состояние исполнения, а не поддельная контрактная строка PASS/FAIL. Ошибка импорта CHECK тоже видна.
- Пустой list от корректного авторского check допускается: в реестре исполнений видно «успешно, 0 строк», не сочинённый PASS. Дубликаты CHECK.id и ссылки APP_IDS вне текущего Run отвергаются.
- Сбой/недоступность ИИ не меняет чисел и PASS/FAIL; отображается явный статус «мнение не получено». Это не считается успешной демонстрацией AI-функции, если она обязательна.

Частичный skip-and-continue на уровне заявок не нужен для первого прототипа. Если команда выбирает его позднее — отдельно определить знаменатели, исключённые ID и критерии полноты, а не применять неявно.

## 12. Исполнение Python, multiuser и данные

### 12.1. Практический минимум — предложение

- RunConfig, Run, код и отчёты имеют owner scope; API проверяет доступ на каждой операции, а не только прячет чужие ID в списке.
- Две браузерные сессии получают разные непрогнозируемые идентификаторы; если нужны реальные учётки/роли, это отдельный объём Q4. Имя из произвольного input не считается аутентификацией.
- Датасеты общие read-only; рабочие и выходные каталоги изолированы по Run. Статические HTML/лог-файлы не обходят ограничения API.
- Длинный Python выполняется вне обработчика UI/HTTP: отдельный worker/процесс или эквивалентное неблокирующее исполнение. Количество одновременно исполняемых задач ограничено; остальные стоят в очереди.
- Задаются конечные wall-time/RAM/объём вывода. Worker не наследует ключи модели, токены и прочие секреты сервера.

**Важное ограничение:** процесс и отдельная папка сами по себе не запрещают сеть, чтение чужих файлов или системные вызовы. Для недоверенных пользователей нужен реально настроенный контейнер/OS-изоляция: отдельный пользователь, ограниченные mount, read-only dataset, отсутствие сети, лимиты и отсутствие секретов. Не объявлять это реализованным без проверки.

Если выбран доверенный локальный режим хакатона, ограничение угроз прямо пишется в README; не открывать такой Python-runner в интернет. Аутентификационная изоляция API не равна защите от произвольного кода с правами сервера.

### 12.2. Персональные данные и LLM

Сырые ответы, код и артефакты не публикуются в открытых логах/репозитории. Для ИИ по умолчанию только обезличенные агрегаты, ограниченные различия и результаты checks; не весь datamart и не произвольные исходные JSON. Согласовать допустимость внешнего провайдера. Тексты данных/проверок считаются данными, не инструкциями для модели. Ответ ИИ помечен как мнение, может быть ошибочным и не меняет детерминированный вердикт.

Срок хранения/удаление и публичность отчётов пока не заданы организаторами. Предлагаемый режим — локальное хранение до конца демо, ручная очистка по README, без публичного доступа по умолчанию. Ключ модели хранится только у серверного компонента, не в браузере и не в окружении пользовательского runner.

## 13. Архитектура и выбор стека

**Не утверждено.** Предлагается модульный монолит плюс изолированное исполнение Python:

```text
Web UI → API / конфигурации / доступ → Orchestrator → Python runner
                                            ↓
    dataset → normalize → vertical UNION → comparison view → counts
                                            ↓                   ↓
                                         MartAPI           pivot / drill-down
                                            ↓                   ↓
                                        checks → финальный отчёт / HTML
                                            ↓
                                  отдельное мнение ИИ
```

Компоненты: UI; API и owner scope; очередь/оркестратор; runner; адаптер хранилища/MartAPI; отчёты; отдельный клиент модели. Dataset-specific код — заменяемые user-code процедуры.

Python обязателен для пользовательских процедур/checks. Язык API/UI, БД, pivot-компонент и способ deployment — выбор команды. Python API + готовый браузерный pivot + SQL/аналитическое хранилище — рабочий кандидат, **не утверждённый стек**. Не вводить Kafka/Kubernetes/распределённый DAG, полноценный Jupyter и собственный pivot-движок без необходимости.

Выбор хранилища проверить на реальных фильтрах MartAPI, группировках и двух одновременных пользователях. Клиенту передавать агрегаты и страницы деталей; если выбран клиентский pivot, обосновать размер именно агрегированных данных и корректность его distinct-итогов.

## 15. План на два дня и критерий готовности

**A:** четыре потока работ, адаптируемые под фактический состав команды. Часы и владельцы не выдумываются; перед стартом команда назначает ответственных.

### Старт: согласование контрактов

Получить ответы на Q1–Q6 либо явно принять безопасные проектные defaults. Зафиксировать входы/выходы процедур, модель вертикального слоя/comparison view, проекцию разрезов, семантику null и режимов массивов. Импорт неизменённого CHECK через минимальный MartAPI проверить до большого UI.

### День 1: сквозной вертикальный срез

- **Данные:** dataset reader → нормализация → сравнение → разрезы → counts; тесты ключей/типов/бакетов.
- **Платформа:** RunConfig, запуск вне request/UI, журнал, runner, owner scope, сохранение артефактов.
- **UI:** конфигурация, оба источника кода, редактор с выполнением и прогресс — не откладывать на конец второго дня.
- **Интеграция:** MartAPI и исходные checks, первая сводка и одно рабочее drill-down.

**Выход дня:** из приложения запуск проходит до минимального отчёта на полном открытом наборе. Консольный расчёт — внутренний checkpoint, но не результат сдачи.

### День 2: закрыть приёмку и защиту

Изменяемая раскладка и корректные distinct-итоги; новый check из UI; общий отчёт и HTML; негативные тесты и два пользователя; ИИ-блок согласно Q1; реальные замеры; README на чистой среде; репетиция.

Если не хватает времени, сокращать оформление, дополнительные графики, сохранение layout, сложную модель ролей, полноценный notebook, streaming и микросервисы. **Q4 — пользователи и ссылки (организаторам/команде).** Достаточно двух независимых серверных сессий с изолированными конфигами/Run или нужны логины/роли? Требуется ли облачный deployment помимо воспроизводимого локального запуска? **Предложение:** приватные session-scoped данные; репозиторий+локальное демо, без публичного user-code runner.

Нужен ответ о корректности, не закрытые материалы жюри.

**Q6 — исполнение и решения команды.** Какой режим разрешён: доверенный локальный Python или недоверенный код с настоящей OS-изоляцией? Кто задаёт лимиты/допустимые зависимости? Есть ли уже утверждённый стек и сколько человек/времени осталось до защиты? **Предложение:** модульный монолит, готовый pivot, минимальный runner с честно описанными ограничениями; полноценные network/FS-запреты заявлять только после реализации и теста.

**Неблокирующее дополнение к ответу организаторов:** обязательна ли отдельная одностраничная записка из плана 01 и есть ли требования к сроку хранения/удалению данных? По остальному использовать явную карточку: оба канала кода нужны; unknown check возможен; 20-минутный сценарий задан; refresh — плюс; streaming — необязателен; готовых normalize/compare нет.

### Исправлено

- Убрано неподтверждённое объявление LLM необязательным.
- Разведены вертикальное хранение, парный интерфейс MartAPI и агрегированные facts.
- Определены грейн, ключи, distinct-метрики, неаддитивность и drill-down без удвоения SOURCE.
- Восстановлены третий режим массивов, бакеты, missing/null/тип и полный контекст modelName.
- Зафиксированы настоящий CHECK/MartAPI, ограниченность APP_IDS, технические статусы без нарушения PASS/FAIL и ограничения исходников checks.
- Уточнены интерактивное редактирование **процедуры и проверки**, снимок кода без полноценного versioning и повтор checks на готовом наборе.
- Временные планки возвращены к их реальному предмету; сценарий сдачи не назван факультативным.
- Добавлены негативные тесты, multiuser/runner threat model и проверяемая матрица приёмки.
- Собраны вопросы, на которые нельзя надёжно ответить из первоисточников; уже отвеченные вопросы сняты.

### Главные риски

1. Q2: противоречивые описания хранения и comparison-контракта; без согласования возможна формальная претензия к модели.
2. Q5: неполная семантика разрезов/нескольких моделей и отсутствие публичного эталона.
3. Q1: ошибочно исключённый ранее ИИ-блок может оказаться обязательным.
4. Python runner, редактор, multiuser и длинный pipeline требуют раннего сквозного прототипа.
5. Готовый pivot может некорректно суммировать distinct-заявки; проверить до оформления UI.
6. Два дня не гарантируют реализацию: пока нет инструмента/тестового отчёта приложения, все AC остаются **планом проверки**, а не пройденной приёмкой.
