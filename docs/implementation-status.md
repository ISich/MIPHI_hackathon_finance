## Реальные стыки перед интеграцией

1. NEXT_STEP явно говорит, что подключаемые пользовательские процедуры, MartAPI, DuckDB/checks и веб-платформа ещё не реализованы в просмотренном срезе. Полный core run не закрывает приёмку приложения.
2. В segments.py PRODUCTS сейчас использует product_name с fallback на product_id; TOP_OFFER также возвращает name/ID. Это отличается от предложенного defaults docs «ID через ;». До wire/schema freeze D1/D4 согласуют единый формат и тест AR-check. Нельзя объявлять один вариант нормативным без источника.
3. PD/cutoff/partner/routing — по репрезентативному продукту (top offer либо сортированный product_id). Это явно документированная, но ещё не подтверждённая заказчиком проекция; полный продуктовый контекст остаётся в comparison.
4. README CLI описывает skip пары с диагностикой, а PRD предлагает строгий FAILED для полного приложения. D2 обязан проверить issues/число обработанных пар и не публиковать неполный прогон как полный; библиотечное поведение не равно политике Run.
5. Некоторые README-комментарии ещё говорят src-layout, тогда как pyproject ищет пакет в корне. При интеграции ориентироваться на реальные файлы и результат clean install, не копировать устаревшее пояснение.
6. Backend/frontend могут начинать независимо от финального DuckDB/MartAPI на согласованных DTO/fixtures. Но runtime/checks нельзя считать подключёнными только по наличию функций ядра.

## Не дублировать работу

Предложенная схема D1–D4 — зоны ответственности, а не приказ переписать всё с нуля. Владельца существующего ядра и заявленного следующего этапа DuckDB/MartAPI нужно назвать до назначения D4 на те же задачи. Если коллега продолжает storage/MartAPI, сохранить его работу и договориться о передаче/перераспределении; не параллелить два несовместимых MartAPI/DB writer.

D2 отвечает за единый storage driver/миграции/политику writer, D4 — analytics/MartAPI запросы; функции reader/compare/segments использовать из существующего пакета через заменяемый этап. При DuckDB не допустить неподдерживаемую многопроцессную запись в один файл: выбрать единый writer, отдельные Run DB либо другой проверенный режим.

До merge docs/core интегратор разрешает ожидаемый конфликт корневых README и сохраняет инструкции обеих частей. Этот docs PR не мерджит `core`, не меняет source code и не деплоит стенд.
