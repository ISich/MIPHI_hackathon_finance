# План интеграции на двухдневный хакатон

**A: порядок работ, не выдуманное расписание команды.** Дедлайн и оставшееся время ожидаются. Не назначать абсолютные часы до ответа; время пересчитаем под реальную защиту.

## Учесть уже выполненную работу

Прочитать [implementation-status.md](implementation-status.md): ветка SomeShit уже содержит ядро, segments и первичную агрегацию. План ниже задаёт gates готовности, не приказ повторить реализованные этапы. Владельцев текущего DuckDB/MartAPI выяснить до новых назначений.

## Gate 0 — договориться об интерфейсах

Все трое (четыре технические зоны): назначить роли, утвердить дерево, сущности Run/Script/Artifact, схемы rows, владельцев и API. Решить блокирующие части `questions.md`; остальные фиксировать как Q с владельцем, не замораживать независимую работу. D2 принимает только совместимые изменения общего контракта.

**Выход:** одинаковые имена полей/статусы; минимальная synthetic fixture и ожидания. Сигнатуры normalize/compare/aggregate пока предложение, CHECK/MartAPI — контракт задания.

## Gate 1 — настоящий минимальный сквозной путь

D1 одна пара → D2 запуск настоящей процедуры выбранным источником → D4 MartAPI и один событийный check → D3 отображение результата по реальному run_id.

**Выход:** UI создаёт Run, журнал отражает вызов, артефакт прочитан, check реально выполнен, ссылка ведёт в результат. Fixtures UI не выдаются за готовый pipeline. Не ждать завершения всего парсера и красоты UI.

## Gate 2 — полный открытый набор, конец первого рабочего дня как ориентир

D1 все массивы/исключения/segments. D2 последовательность этапов, сохранение, owner scope. D4 пять checks, корректные counts+membership. D3 оба источника кода, мониторинг, summary и один drill-down.

**Выход:** UI → полный набор → завершённый отчёт. Если не проходит — весь следующий интеграционный интервал идёт на сквозной путь, не на дополнительные графики/LLM.

## Gate 3 — обязательные пользовательские сценарии

Настраиваемая раскладка, полное membership/pagination, изменение процедуры и новая проверка в UI, отдельный check-run на готовом dataset artifact, общий отчёт, HTML→сводная. Две пользовательские сессии. Индексы и реальные замеры. ИИ/Codex явно отложен пользователем: подключать только после готовности и проверки ядра, с честной ошибкой при недоступности.

**Выход:** AC-01…AC-22 распределены и выполнены либо помечены blocked/failed с причиной; незавершённые функции не считаются готовыми.

## Gate 4 — freeze и защита

Прекратить изменение DTO/схем без согласия всех consumers. Чистый запуск по README; если демо идёт со стенда, стенд проходит readiness и browser smoke; репетиция девяти шагов PRD §15. Сохранить commit, ревизию данных и реальные замеры. После freeze — только исправления, подтверждённые тестом.

## Порядок небольших PR — предложение до соглашений команды

1. Общие contracts/fixtures/docs.
2. D2 Run/runtime shell; D1 processing fixture; D4 MartAPI fixture; D3 API client/workspace — независимые небольшие PR после общих схем.
3. Первый сквозной integration PR (не один огромный merge в конце).
4. Полный dataset/checks/reporting и negative tests.
5. Acceptance/demo/runbook.

Названия веток, reviewers и CI определяются фактическими соглашениями. Не создавать четыре несовместимые ветки, меняющие один storage driver/DTO без общего steward.

## Правила выхода из блокировок

- Нет эталона: продолжаем тесты, но AC-07 = BLOCKED, не PASS.
- Нет ответа по AI: ядро не зависит от модели; объём AI не объявляется закрытым.
- Нет доступа к стенду: локальная приёмка отдельно, deploy = BLOCKED.
- Не выбран формат числа/null: вынести в policy процедуры, записать влияние на expected. Не менять молча после получения эталона.
