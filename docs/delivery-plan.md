Не ждать завершённого UI, чтобы дать рабочие status/events/report endpoints.

Подключить checks через MartAPI, выбрать с Павлом DuckDB writer policy, добавить недостающие CHANGE_TYPE/segments/membership в facts, rollup+drill-down и HTML через согласованные порты. Обёртки процедур должны оставаться заменяемыми Python, не зашитыми в платформу.
3. **Frontend-участник — D3, локальный Codex.** Сначала отличить sandbox network от DNS Mac, получить docs, установить/проверить Playwright+Chromium. Реализовать config, редактор+выполнение, Run monitor, report/pivot/drill-down/checks/export. Ранние API fixtures маркировать, перейти к реальному API в первом вертикальном срезе.

Если D1+D4 не успевает, Павел помогает со storage driver/HTTP publication HTML, D3 — с отображением/версткой экспортируемого документа. Не заводить второй MartAPI/runner; алгоритмы и семантические тесты остаются у data owner. Review D1↔D4 выполняет другой человек, а не автор сам себе.

## Стек: закрыть один раз в начале

Кандидат для быстрого старта: Python/FastAPI backend, существующий decision_diff как библиотека с выбираемыми wrappers, DuckDB для аналитики, SQLite для Run metadata при необходимости, React+TypeScript+Vite frontend. Это **предложение капитана**, не утверждение уже принятого стека; если участники уже начали на другом совместимом стеке, не переписывать ради названий. При DuckDB выбрать и проверить single-writer/per-Run DB модель; одна DB и несколько произвольных writers не допускаются без доказанной поддержки.
